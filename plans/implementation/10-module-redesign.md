# 10. 모듈·전투 그리드 재설계

## 역할

이 단계는 06.5 중간 구현 평가 이후, 기존 모듈 설치 구조와 07 진행 콘텐츠 사이에 삽입되는 필수 전환 단계다. 파일명은 기존 계획의 07~09 순서를 보존하기 위해 10을 사용하지만 실제 실행 순서는 `06.5 → 10 → 07 → 08 → 09`다.

승인된 설계 명세:

- [모듈·전투 그리드 재설계 명세](../../docs/superpowers/specs/2026-08-31-module-grid-redesign-design.md)

## 목표

1. `CORE`, `RESOURCE`, `GATHERER`, `RECYCLER`, `ARSENAL`, `COMPOSER`, `RAIL`, `POWER_PACK`, `CATERPILLAR_TRACK`, `ARMOR_PLATE`를 탱크 생성 시 활성화된 내장 시스템으로 전환한다.
2. 격자에는 `DIRECT_WEAPON`, `ARC_WEAPON`과 이후 추가될 전투 모듈만 설치한다.
3. `src/data/tanks/<tankId>/module.json`과 같은 디렉터리의 `<moduleId>.json`으로 탱크별 콘텐츠를 로드한다.
4. 우측 패널에서 모듈별 JSON 업그레이드 트리를 선택하고, 한 분기만 현재 런에 남긴다.
5. 1x1·2x1·2x2 등 여러 크기의 전투 모듈을 겹침 없이 배치한다.

## 변경 원칙

- Canvas와 현재 설치된 TypeScript/Vite 의존성만 사용한다. 새 UI 프레임워크와 데이터베이스는 추가하지 않는다.
- 기존 전투·자원 수치와 일시정지 규칙을 가능한 한 유지하고 설치 단위와 업그레이드 경로만 변경한다.
- JSON에는 임의 코드나 수식을 넣지 않고, TypeScript가 허용한 효과 키와 `add`·`multiply` 연산만 허용한다.
- 내장 시스템은 레벨 1·활성 상태로 시작하며, 1차 버전에서는 개별 격자 피격·파괴·수리를 제공하지 않는다.
- 전투 모듈 회전·업그레이드 초기화·복잡한 DAG·그래프 팬/줌은 구현하지 않는다.

## 구현 순서

### 1. 콘텐츠 계약과 기본 JSON

1. 탱크 정의, 모듈 정의, 전투 모듈 크기, 배치, 업그레이드 노드, 효과의 TypeScript 타입을 정한다.
2. `starter/module.json`에 현재 기본 탱크의 3x3 그리드와 코어 칸을 정의한다.
3. 코어와 모든 비전투 시스템의 `<moduleId>.json`을 만든다.
4. 직사·곡사 전투 모듈 JSON을 만들고 현재 기본 수치·설치 비용·동작 키를 옮긴다.
5. 모든 모듈 JSON에 중앙 `root`와 최소 2개의 자식 선택지를 넣어 그래프 동작을 검증한다. 파생 노드는 대표 모듈부터 추가하고 밸런스는 09단계에서 조정한다.

확인:

- JSON만 읽어도 탱크 그리드, 기본 시스템, 초기 전투 배치, 모듈 크기, 업그레이드 비용을 알 수 있다.
- `builtinModuleIds`에는 설치 대상이 아닌 시스템만 들어간다.
- 전투 모듈 `size`는 양의 정수다.

### 2. 로더와 콘텐츠 검증

1. `src/data/tanks/*/module.json`을 Vite JSON 모듈 자동 발견으로 등록한다.
2. 선택 탱크가 참조하는 `<moduleId>.json`을 같은 디렉터리에서 읽는다.
3. ID 중복, 누락 파일, 잘못된 분류·동작 키, 비용·크기 범위, 순환 부모, 중복 부모 자식, 잘못된 효과 키를 검증한다.
4. 초기 배치를 임시 `CombatGrid`에 넣어 경계·코어 칸·금지 칸·겹침을 검증한다.
5. 오류는 파일·필드를 포함한 초기화 실패 메시지와 개발자 콘솔로 노출한다.

확인:

- 유효한 `starter` 정의가 로드된다.
- 깨진 JSON이 부분 로드 없이 실패한다.
- 새 탱크 디렉터리를 추가할 수 있는 로더 반환 형태가 고정된다.

### 3. 내장 시스템 이전

1. `VehicleSystems`에 코어 HP, 이동, 장갑, 생산·수집·변환·물류 상태를 둔다.
2. `Module.ts`의 비전투 모듈 타이머와 기능을 내장 시스템 업데이트로 옮긴다.
3. 현재 생산 규칙을 유지한다.
   - 자원 생산기: 1초마다 resource 10
   - Recycler: resource 10 → matter 5, 1초
   - Arsenal: matter 5 → ammo 1, 1.5초
   - Composer: matter 10 → nano 1, 2.5초
4. 수집 반경, 이동 속도, 궤도 제한, 장갑 계산을 내장 시스템의 유효 수치에서 읽는다.
5. Rail은 내장 물류 시스템으로 이전하고 생산 출력 버퍼를 저장고로 전달하는 단일 경로를 유지한다.
6. 일시정지 중에는 생산·수집·물류 타이머를 증가시키지 않는다.
7. 내장 시스템에는 설치 버튼·그리드 좌표·개별 피격 HP를 부여하지 않는다.

확인:

- 시작 시 별도 설치 없이 모든 내장 시스템이 작동한다.
- 생산→변환→탄약→발사 사이클이 기존과 동일하게 재현된다.
- 내장 시스템 JSON 업그레이드 수치가 런타임 효과에 연결된다.

### 4. 전투 모듈과 다중 칸 그리드

1. `CombatGrid`를 탱크 정의의 columns, rows, coreCell, blockedCells로 생성한다.
2. 배치의 좌상단 `anchor`와 모듈 JSON의 `size`로 전체 점유 칸을 계산한다.
3. 경계·금지 칸·기존 점유 칸 검사를 단일 `canInstall()` 경로에 둔다.
4. 기존 `Vehicle.modules[y][x]` 순회를 `CombatGrid.getPlacements()`와 `getModuleAtCell()` 조회로 바꾼다.
5. 다중 칸 모듈은 하나의 인스턴스로 업데이트하고 조준점과 렌더링 중심은 점유 영역 중앙으로 계산한다.
6. 방향 피해가 점유 칸 중 하나를 조회해도 같은 전투 모듈에 전달한다.
7. 모듈 회전은 지원하지 않고 JSON의 가로·세로 방향을 그대로 사용한다.
8. `kind: "combat"`인 모듈만 설치 대상으로 허용한다.

확인:

- 1x1, 2x1, 2x2 모듈이 각각 설치·렌더링된다.
- 코어 칸·그리드 밖·겹침 설치가 모두 실패한다.
- 초기 배치와 런 중 설치가 동일한 검사 경로를 사용한다.

### 5. 업그레이드 매니저

1. 모듈별 트리와 현재 런의 선택 노드 집합을 관리한다.
2. 중앙 root는 자동 해금하고 같은 `parentId`의 노드를 배타적 선택 그룹으로 취급한다.
3. `getNodeStates`, `canSelect`, `select`, `getEffectiveStats`, `reset` API를 구현한다.
4. `select()`는 가용성 확인 → 비용 지불 → 선택 기록 → 형제 잠금 → 누적 효과 재계산 순서로 원자적으로 처리한다.
5. 자원 부족·잠긴 노드·이미 선택된 노드는 상태와 자원을 바꾸지 않는다.
6. 효과는 허용된 stat과 `add`·`multiply` 연산만 적용한다.
7. 재시작 시 선택 상태를 초기화하고 런 중에는 선택한 가지를 되돌리지 않는다.

확인:

- 한 노드 선택 후 형제와 하위 노드 상태가 `disabled` 또는 `locked`로 바뀐다.
- 선택 효과가 다음 업데이트부터 내장 시스템 또는 전투 모듈에 반영된다.
- 모듈별 선택 상태가 서로 섞이지 않는다.

### 6. 게임 루프 연결

1. `Game` 초기화에서 탱크 정의를 로드하고 `VehicleSystems`, `CombatGrid`, `UpgradeManager`를 생성한다.
2. `Vehicle`은 탱크 정의와 전투 그리드만 보유하고 이동 속도·장갑·코어 HP는 내장 시스템에서 읽는다.
3. 게임 루프에서 내장 시스템을 먼저 업데이트한 뒤 전투 모듈을 업데이트한다.
4. 생산 출력, 탄약 소비, 적 피해, 승패, 재시작을 새 객체 경계에 연결한다.
5. 일시정지 요청은 기존 `GameState`를 유지하고 관리 입력만 통과시킨다.
6. 차량 이동 경계는 우측 패널 영역을 침범하지 않도록 HUD 패널 폭을 반영한다.

확인:

- 기존 전투·자원·승패 흐름이 새 모듈 구조에서 재현된다.
- 일시정지 중 자동 진행과 관리 입력의 차이가 유지된다.
- 재시작 시 탱크 정의는 같고 런타임 상태만 초기화된다.

### 7. 우측 업그레이드 패널

1. 기존 하단 전체 상점과 단일 업그레이드 버튼을 제거한다.
2. 우측 패널에 내장 시스템·전투 모듈 목록과 현재 선택 대상을 표시한다.
3. 선택한 모듈의 root, 자식, 파생 노드를 깊이·형제 순서로 자동 배치한다.
4. 부모-자식 연결선과 selected·available·locked·disabled 상태를 그린다.
5. 빈 전투 칸을 선택하면 같은 패널을 전투 모듈 설치 목록으로 바꾼다.
6. 패널 hitbox를 먼저 처리해 그리드 클릭과 중복되지 않게 한다.
7. 노드가 패널 높이를 넘으면 그래프 영역을 클리핑하고 최소 스크롤 상태를 제공한다.
8. 설치·업그레이드 실패 사유를 패널 피드백으로 표시한다.

확인:

- 내장 시스템을 설치하려는 경로가 없다.
- 선택지 하나를 고르면 다른 선택지와 파생 가지가 시각·입력 양쪽에서 비활성화된다.
- 패널을 통해서만 전투 모듈 설치와 업그레이드를 수행할 수 있다.

### 8. 문서와 회귀 검증

1. `plans/system.md`를 내장 시스템·전투 전용 그리드·JSON 규칙에 맞게 갱신한다.
2. `plans/user_guide.md`에서 하단 상점, 일반 모듈 설치, 단일 업그레이드 설명을 제거한다.
3. 07~09 계획의 선행 조건과 검증 항목을 확인한다.
4. `npm run build`, `git diff --check`, 유효·오류 JSON 로드, 1x1·2x1·2x2 검사, 분기 잠금, 일시정지·재시작·승패 회귀를 수행한다.

## 완료 기준

- 게임 시작 시 모든 비전투 시스템이 활성화되고 하단 설치 상점이 없다.
- 우측 패널에서 모듈별 JSON 그래프를 열고 분기 업그레이드를 진행할 수 있다.
- 전투 모듈만 탱크별 그리드에 설치할 수 있다.
- 전투 모듈의 크기와 점유 검사가 렌더링·피해·조준과 일치한다.
- 기존 자원 생산·탄약·전투·일시정지·승패·재시작 흐름이 유지된다.
- 잘못된 콘텐츠가 명확히 실패하고 유효한 새 탱크 디렉터리를 추가할 수 있다.
- `npm run build`와 `git diff --check`가 통과한다.
