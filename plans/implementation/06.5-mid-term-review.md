# 06.5. 중간 구현 점검

## 현재 적용 계획: 모듈·전투 그리드 재설계 통합

06.5는 기존 구현 점검만 수행하는 단계가 아니라, 이번 신규 요구사항을 반영하는 필수 전환 단계다. 별도 10단계는 실행하지 않으며, 실제 순서는 `06.5(재설계 포함) → 07 → 08 → 09`다.

승인된 설계 명세:

- [모듈·전투 그리드 재설계 명세](../../docs/superpowers/specs/2026-08-31-module-grid-redesign-design.md)

### 목표

1. 기존 01~06 구현의 회귀 위험을 점검한다.
2. `CORE`, `RESOURCE`, `GATHERER`, `RECYCLER`, `ARSENAL`, `COMPOSER`, `RAIL`, `POWER_PACK`, `CATERPILLAR_TRACK`, `ARMOR_PLATE`를 탱크 생성 시 활성화된 내장 시스템으로 전환한다.
3. 격자에는 전투 모듈만 설치하고 1x1·2x1·2x2 다중 칸 점유를 지원한다.
4. `src/data/tanks/<tankId>/module.json`과 같은 디렉터리의 `<moduleId>.json`을 기준으로 탱크·모듈·업그레이드 콘텐츠를 로드한다.
5. 우측 패널의 노드 그래프에서 모듈별 업그레이드 분기와 형제 잠금을 처리한다.

### 선행 조건

- 01~06 구현이 현재 브랜치에 존재한다.
- [06.5 기존 점검 기록](#이전-점검-기록재설계-전)이 회귀 검토 자료로 확인된다.
- 승인된 설계 명세와 현재 구현 문서를 기준으로 진행한다.

### 작업 순서

#### 1. 기준선 고정과 콘텐츠 계약

1. 현재 코드의 `tsc --noEmit`, `git diff --check`, 브라우저 시작·이동·전투·일시정지·재시작을 기준선으로 기록한다.
2. 탱크 정의, 모듈 정의, 업그레이드 노드, 제한된 효과 키의 TypeScript 타입을 정한다.
3. `src/data/tanks/starter/module.json`에 현재 3x3 그리드, 코어 칸, 내장 시스템 ID, 초기 전투 모듈 배치를 정의한다.
4. 같은 디렉터리에 코어·비전투 시스템·직사·곡사 모듈의 `<moduleId>.json`을 만든다.
5. 모든 모듈 JSON의 업그레이드 트리에 중앙 root와 2개 이상의 자식 선택지를 넣어 데이터 계약을 검증한다.

#### 2. 로더와 콘텐츠 검증

1. Vite JSON 자동 발견으로 탱크 디렉터리의 `module.json`을 읽는다.
2. `module.json`이 참조하는 `<moduleId>.json`을 같은 디렉터리에서 읽는다.
3. ID·파일 누락, 분류·동작 키, 비용·크기, 순환 부모, 중복 선택지, 잘못된 효과 키를 검증한다.
4. 초기 배치를 임시 전투 그리드에 넣어 경계·코어 칸·금지 칸·겹침을 검증한다.
5. 오류는 파일과 필드를 포함한 초기화 실패 메시지로 노출하고 부분 로드는 허용하지 않는다.

#### 3. 내장 시스템 이전

1. `VehicleSystems`에 코어 HP, 생산·수집·변환·물류, 이동, 장갑 상태를 둔다.
2. `Module.ts`의 비전투 모듈 타이머와 기능을 내장 시스템 업데이트로 이전한다.
3. 기존 생산 규칙인 자원 생산기 1초/resource 10, Recycler 1초/resource 10→matter 5, Arsenal 1.5초/matter 5→ammo 1, Composer 2.5초/matter 10→nano 1을 유지한다.
4. Rail은 내장 물류 경로로 이전하고 생산 출력 버퍼를 저장고로 전달한다.
5. 이동 속도, 궤도 제한, 장갑 계산은 내장 시스템의 유효 수치에서 읽는다.
6. 내장 시스템은 설치 버튼·그리드 좌표·개별 격자 피격 HP를 갖지 않으며, 1차 구현에서는 항상 활성 상태다.
7. 일시정지 중 생산·수집·물류·이동·전투 타이머를 진행하지 않는다.

#### 4. 전투 전용 다중 칸 그리드

1. 탱크 정의의 columns, rows, coreCell, blockedCells로 `CombatGrid`를 만든다.
2. 전투 모듈 JSON의 `size`와 좌상단 `anchor`로 점유 칸을 계산한다.
3. 경계·금지 칸·기존 점유 칸 검사를 단일 `canInstall()` 경로에 둔다.
4. 기존 `Vehicle.modules[y][x]` 순회를 전투 배치 목록과 점유 칸 조회로 바꾼다.
5. 다중 칸 모듈은 하나의 인스턴스로 조준·업데이트·피격·렌더링하고, 중심은 점유 영역 중앙으로 계산한다.
6. 회전은 1차 범위에서 제외하며 `kind: "combat"`인 모듈만 설치 대상으로 허용한다.

#### 5. JSON 업그레이드 그래프

1. `UpgradeManager`가 모듈별 트리와 현재 런의 선택 노드를 보관한다.
2. root를 자동 해금하고 같은 `parentId`의 자식 중 하나만 선택 가능하게 한다.
3. 선택 가능성 확인 → 비용 지불 → 선택 기록 → 형제·하위 가지 잠금 → 효과 재계산을 원자적으로 처리한다.
4. 효과는 허용된 stat과 `add`·`multiply`만 적용하고 임의 JSON 코드는 실행하지 않는다.
5. 재시작 시 선택 상태를 초기화하며 런 중에는 선택한 분기를 되돌리지 않는다.

#### 6. 게임 루프와 우측 패널 연결

1. `Game` 초기화에서 탱크 정의, `VehicleSystems`, `CombatGrid`, `UpgradeManager`를 연결한다.
2. `Vehicle`은 전투 그리드만 보유하고 이동·장갑·코어 HP는 내장 시스템에서 읽는다.
3. 내장 시스템을 먼저 업데이트한 뒤 전투 모듈을 업데이트하고, 기존 자원·탄약·승패 흐름을 연결한다.
4. 하단 전체 모듈 상점과 단일 업그레이드 버튼을 제거한다.
5. 우측 Canvas 패널에 내장 시스템·전투 모듈 목록, 중앙 root, 자식·파생 노드, 비용·효과·상태를 표시한다.
6. 빈 전투 칸을 선택했을 때만 전투 모듈 설치 목록을 표시하고 패널 hitbox를 먼저 처리한다.
7. 우측 패널 폭을 차량 이동 경계에 반영한다.

#### 7. 문서·검증 갱신

1. `plans/system.md`와 `plans/user_guide.md`에서 일반 모듈 설치·하단 상점·단일 업그레이드 설명을 제거한다.
2. 07~09 계획의 선행 조건을 이 통합 단계 기준으로 확인한다.
3. 잘못된 JSON, 1x1·2x1·2x2 배치, 분기 잠금, 효과 반영, 일시정지·재시작·승패 회귀를 검증한다.
4. `npm run build`와 `git diff --check`를 실행한다.

### 완료 기준

- 06.5 하나의 구현 단계에서 기존 회귀 점검과 신규 모듈 구조 전환이 완료된다.
- 게임 시작 시 모든 비전투 시스템이 별도 설치 없이 활성화된다.
- 전투 모듈만 탱크별 그리드에 설치되며 다중 칸 검사와 렌더링이 일치한다.
- 모듈별 JSON 업그레이드 그래프에서 선택·비용·효과·형제 잠금이 동작한다.
- 우측 패널이 기존 하단 전체 상점을 대체한다.
- 기존 생산·탄약·전투·일시정지·승패·재시작 흐름이 유지된다.
- 07단계가 06.5의 완료 결과만 선행 조건으로 삼아 바로 진행할 수 있다.
- `tsc --noEmit`, `npm run build`, `git diff --check`와 브라우저 수동 검증이 통과한다.

01~06 구현 완료 기준과 현재 코드·실행 경로를 대조해 남은 기능 누락, 문서 불일치, 검증 환경 문제를 기록한다.

## 점검 결과

### 1. 처치된 적의 지연 충돌 피해

- 위치: `src/core/Game.ts`의 적 업데이트·충돌 처리
- 현재 문제: 발사체로 이미 처치된 적이 배열에서 제거되기 전에 `enemy.isDead()` 확인 없이 코어 충돌 검사를 통과할 수 있다.
- 영향: 죽은 적이 한 프레임 동안 차량에 피해를 주며, 03 전투 MVP의 처치·피해 규칙과 어긋난다.
- 후속 조치: 적 업데이트와 충돌 판정 전에 사망 적을 제거하거나 즉시 건너뛴다. 처치 보상은 현재처럼 한 번만 생성한다.

### 2. Rail 장거리 운송의 실행 경로 부재

- 위치: `src/entities/Vehicle.ts`, `src/entities/Module.ts`, `src/core/Game.ts`
- 현재 문제: 차량 격자가 3×3이고 코어가 중앙이므로 모든 설치 칸이 코어 기준 Chebyshev 거리 1 이내다.
- 영향: `RailModule.transfer()`는 구현되어 있지만, HUD를 통해 자연 수집 범위 밖의 생산 모듈을 만들 수 없어 장거리 운송을 실제 플레이에서 재현할 수 없다.
- 후속 조치: 코어 레벨에 따른 격자 확장과 확장 격자의 설치·렌더링·자연 수집 경계를 연결한 뒤 Rail 장거리 시나리오를 검증한다.

### 3. 일부 모듈 업그레이드 효과 누락

- 위치: `src/entities/Module.ts`의 `RecyclerModule`, `ArsenalModule`, `MatterComposerModule`, `RailModule`
- 현재 문제: 공통 업그레이드로 레벨과 비용은 증가하지만 생산 간격, 생산량, 운송량 등 실제 성능 수치가 레벨을 사용하지 않는다.
- 영향: 02 모듈 기반 정리의 “업그레이드 후 성능과 비용 갱신” 기준을 충족하지 못한다.
- 후속 조치: 각 모듈별로 생산 간격 또는 생산량·출력 버퍼·운송량 중 적용할 수치를 확정하고 레벨 계산식과 문서를 함께 갱신한다.

### 4. 관통력의 실제 전투 연결 누락

- 위치: `src/entities/Vehicle.ts`, `src/core/Game.ts`, `src/entities/Projectile.ts`
- 현재 문제: `Vehicle.takeDamage()`와 Armor Plate 계산식은 관통력 인자를 지원하지만, 실제 게임 호출은 관통력 0만 전달한다. 발사체에도 관통력 설정이 없다.
- 영향: 장갑 수치 계산은 실행되지만 장갑보다 높은 관통력의 공격을 플레이 중 재현할 수 없다.
- 후속 조치: 적 공격 또는 공격 발사체에 관통력 수치를 부여하고, 모든 차량 피해 입력이 동일한 피해 패킷 경로를 사용하도록 연결한다.

### 5. 초기 배치 문서 불일치

- 위치: `plans/user_guide.md`, `src/entities/Vehicle.ts`
- 현재 문제: 사용자 가이드는 시작 시 곡사 무기가 있다고 설명하지만, 현재 초기 차량에는 곡사 무기가 설치되어 있지 않다.
- 후속 조치: 초기 배치를 유지할 경우 가이드에서 곡사 무기를 제거하고, 시작 장비로 제공할 경우 차량 초기 배치와 자원 밸런스를 함께 수정한다.

### 6. `power` 자원 설계와 현재 MVP 저장소 불일치

- 위치: `plans/system.md`, `src/core/ResourceStorage.ts`, `plans/implementation/05-production-and-logistics.md`
- 현재 문제: 시스템 문서는 코어·Power Pack의 `power` 생산과 저장을 정의하지만, 현재 MVP 저장소는 `resource`, `matter`, `ammo`, `nano` 네 종류만 제공한다.
- 후속 조치: `power`를 다음 경제 단계에서 구현할지 결정하고, 구현 전까지는 시스템 문서에서 현재 MVP와 미래 설계를 명확히 분리한다.

### 7. 초기 모듈의 격자 좌표 데이터 불일치

- 위치: `src/entities/Vehicle.ts` 초기 배치
- 현재 문제: Resource Module과 Direct Weapon Module은 배열상의 위치와 생성자에 전달한 `gridX/gridY`가 서로 뒤바뀌어 있다.
- 영향: 현재 렌더링과 대부분의 동작은 배열 인덱스를 사용해 동작하지만, 향후 위치 기반 피해·우선순위·이동 기능에서 잘못된 좌표가 사용될 수 있다.
- 후속 조치: 초기 모듈의 배열 인덱스와 모듈 좌표를 일치시키고, 모듈 위치 기준 테스트를 추가한다.

- 02: 공통 모듈 HP, 설치·업그레이드, 비활성화 처리 구현

## 검증 환경

- `tsc --noEmit`: 통과
- Vite 대체 출력 경로 빌드: 통과
- `git diff --check`: 통과
- 별도 테스트 스크립트는 아직 없으므로 전체 게임 루프의 자동 회귀 검증은 부족하다.
- 기본 `npm run build`는 코드 오류가 아니라 기존 `dist/assets` 디렉터리의 Windows 권한 오류로 실패한다.
