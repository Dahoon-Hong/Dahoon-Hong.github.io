# 12.9 적 collision 성능 예산과 frame drop 제거

상태: 구현 완료 (자동 검증 2026-09-14, runtime QA 대기)
상위 plan: [12. 적 시야 우선 추적 및 A* Web Worker 분리](12-enemy-navigation-worker-priority.md)
선행 subplan:

- [12.7 적 자연스러운 밀어내기와 spawn admission](12.7-enemy-natural-push-and-spawn-admission.md)
- [12.8 적 collider 밀도 조정](12.8-enemy-collider-density.md)

## 목적

적 수가 증가하면 여전히 frame drop이 발생한다. 현재 구현에는 성능상 큰 비용이
겹쳐 있다.

- `Game.update()`가 `enemyCollision.separate()`를 이동 전·후 두 번 호출한다.
- `separate()`가 최대 8회 spatial index를 다시 build한다.
- 각 pair에서 여러 ring·각도 후보를 terrain-safe로 검사한다.
- `EnemySpatialIndex.query()`가 local 후보를 모두 수집하고 정렬한다.
- navigation coordinator와 collision resolver가 각각 spatial index와 nearby list를
  계산한다.

자연스러운 push로 동작을 바꾼 뒤에도 중복 계산을 제거하지 않으면 적 수가 많은
fixture에서 같은 문제가 재현될 수 있다. 이 subplan은 collision work를 한 번의
bounded neighbor pass로 제한하고, 실제 frame time을 observer에서 측정 가능하게
한다.

## 요구사항 및 범위

### 포함

- 한 simulation update에 spatial index build를 한 번만 수행한다.
- coordinator가 가진 neighbor snapshot을 collision resolver가 재사용한다.
- pair별 반복 depenetration pass, ring probe, fallback 후보 정렬을 제거한다.
- 적별 collision neighbor 조회 수를 policy 상한으로 제한한다.
- `EnemySpatialIndex`가 max 결과보다 많은 후보를 전체 정렬하지 않도록 nearest
  bounded 조회를 제공한다.
- 적별 push 계산을 `O(enemyCount × boundedNeighbors)`로 유지한다.
- collision 계산 시간·pair 수·neighbor 수·terrain blocked push를 DEV telemetry로
  기록한다.
- raw frame delta와 지속 frame drop도 DEV observer에서 확인한다.
- 160/320/640 적 fixed load를 같은 canonical fixture에서 비교한다.

### 제외

- collision을 별도 Web Worker/thread로 이동
- SharedArrayBuffer, lock, physics engine 도입
- A* Worker pool 확대, flow field, heap, HPA
- production runtime에 observer 노출
- collider 수치 자체 조정(12.8에서 처리)

## 선택 설계

### 1. frame snapshot 공유

`EnemyNavigationCoordinator.update()`가 이미 frame 시작 시 spatial index를
build하고 적별 nearby list를 생성한다. collision resolver는 두 번째 index를
만들지 않고 이 결과를 입력으로 받는다.

권장 흐름:

1. Game이 vehicle·target snapshot을 만든다.
2. coordinator가 생존 적을 한 번 index에 등록하고 bounded neighbor snapshot을
   만든다.
3. collision resolver가 snapshot을 읽어 적별 push intent와 collision telemetry를
   계산한다.
4. Enemy가 navigation intent와 collision push를 합산해 terrain-safe 이동한다.
5. Game은 차량 contact와 death 정리만 수행한다.

현재 coordinator의 `maxNearbyEnemies`를 기본 collision neighbor 상한으로
재사용한다. 실제 collision에 더 많은 이웃이 필요하다는 증거가 생길 때만 별도
`maxCollisionNeighbors`를 추가한다.

### 2. bounded nearest query

`EnemySpatialIndex.queryAt()`은 현재 후보를 배열에 모은 뒤 전체 sort한다.
`maxResults`가 작을 때는 고정 길이 nearest 목록을 유지하는 방식으로 바꿔
bucket 후보 전체 sort를 없앤다. 거리 비교는 가능한 경우 제곱 거리로 처리하고,
최종 방향 계산에서만 `Math.hypot`을 사용한다.

collision resolver는 다음을 하지 않는다.

- pair마다 후보 ring을 여러 번 terrain sampling
- 같은 frame에서 index 재build
- 모든 적 배열을 대상으로 O(N²) 전체 비교
- 실패한 후보를 최대 8 pass로 재시도

terrain 검사는 실제 enemy movement의 기존 `getSafeRadiusProgress()`에 맡긴다.
push가 terrain에 막히면 `collisionBlockedPushes`만 기록하고 다른 후보 위치를
찾기 위해 추가적인 전역 search를 실행하지 않는다.

### 3. telemetry와 budget

DEV observer에 다음 aggregate 값을 추가한다.

- `collisionMainMs`
- `collisionMainMsP95`
- `collisionPairsThisFrame`
- `collisionPushesThisFrame`
- `collisionBlockedPushesThisFrame`
- `collisionCandidatesTotal`
- `collisionCandidatesMax`
- `spawnSkippedEnemies`
- `frameDeltaMs`
- `frameOverBudgetCount`

`frameDeltaMs`는 `requestAnimationFrame` timestamp 차이이며, simulation에
사용하는 capped `dt`와 분리한다. `frameOverBudgetCount`는 33.3ms를 넘긴 frame을
기록하되, 단일 browser scheduling spike와 지속적인 계산 병목을 구분할 수 있게
연속 초과 횟수도 내부에 둔다.

초기 완료 기준은 절대적인 특정 장치 성능보다 같은 runtime의 before/after를
사용한다.

- collision 계산은 enemy 수에 대해 선형에 가까운 증가를 보인다.
- 160→640에서 collision pair/query work가 4배를 크게 넘지 않는다.
- 1분 관측 중 33.3ms 초과 frame이 연속 3회 이상 발생하지 않는다.
- 320 load의 collision p95가 4ms 이하이고, 640 load에서도 8ms 이하를 목표로
  한다. 단발 scheduling spike는 별도 기록한다.
- 자연스러운 push가 막히는 경우에도 frame loop가 멈추거나 queue가 무한히
  증가하지 않는다.

이 수치는 첫 runtime 결과로 재조정할 수 있지만, 기준 변경은 별도 기록 없이
완화하지 않는다.

### 4. thread/Worker 판단

collision은 매 frame의 최신 적 위치와 navigation 의도를 읽고 즉시 다음 이동에
반영해야 한다. 이를 Worker로 보내면 위치 snapshot 구조화 복사, 결과 동기화,
stale push 폐기 비용이 생긴다. 현재 병목은 반복적인 main-thread 보정과 중복
spatial query이므로 먼저 bounded main-thread 계산으로 해결한다.

동일 fixture에서 bounded 계산 후에도 collision p95가 기준을 넘을 때만 별도
Worker/physics 계획을 검토한다. 이번 subplan에서 thread를 추가하지 않는다.

## 자동 테스트

- 한 frame의 collision index build 횟수가 1회다.
- query max가 8일 때 8개를 넘는 후보를 반환하지 않고, nearest 순서가 유지된다.
- dead enemy가 query와 collision pair에 포함되지 않는다.
- 160/320/640 synthetic enemy에서 pair 비교가 전체 조합 수가 아니라 bounded
  neighbor 수에 비례한다.
- push intent 계산 뒤 `Enemy.update()`의 terrain-safe 이동 결과가 기존 terrain
  계약과 같다.
- vehicle contact guard가 collision optimization으로 제거되지 않는다.
- telemetry가 production flag가 꺼진 상태에서는 DOM에 노출되지 않는다.
- worker-on/off navigation과 collision snapshot 공유가 stale state를 만들지 않는다.

## Runtime QA

필수 fixture:

- URL: `?test=1&scenario=enemy-collision-stress&worker=on`
- map: `aurelia/landing-zone`
- vehicle armor: `100`
- game over: disabled
- fixed loads: 160 → 320 → 640을 각각 새로고침해 한 bounded 실행에서 비교하거나,
  fixture count query가 지원되면 640에서 160/320 baseline을 함께 기록

기대 시간은 1분이고 절대 최대는 4분이다. 정상 결론에 4분을 사용하지 않는다.

- 0:00~0:15: Worker init, armor 100, enemy count, observer와 frame metric 확인
- 0:15~0:35: 160/320 load에서 collision p95·neighbor/pair count 확인
- 0:35~0:50: 640 load에서 frame delta, collision p95, stuck·terrain safety 확인
- 0:50~1:00: queue, worker fallback, console과 최종 metric 기록
- 지속 frame drop, 계산 폭주, 적 정지·관통·영구 겹침이 확인되면 최소 증거만
  남기고 즉시 `FAIL`로 종료한다.

통과 기준:

- collision index build가 frame당 1회이고, pre/post full separation pass가 없다.
- collision work가 bounded neighbor 수에 비례하고 160→640에서 quadratic burst가
  나타나지 않는다.
- 320 load collision p95 ≤ 4ms, 640 load collision p95 ≤ 8ms 목표를 충족한다.
- 33.3ms 초과 frame이 연속 3회 이상 발생하지 않는다.
- `terrainUnsafe=0`, 지속 `stuck=0`, GAME_OVER 없음
- Worker queue/fallback이 무한 증가하지 않는다.
- console error와 runtime exception이 없다.

## 완료 기준

- 적 수 증가에도 collision 계산이 bounded neighbor 기반으로 유지된다.
- 자연스러운 push와 collider density 변경을 포함한 최종 fixture에서 frame drop이
  재현되지 않거나 원인이 명확히 분리된다.
- thread/Worker 추가 없이 main-thread collision 비용을 수치로 확인할 수 있다.
- 단위 테스트, build, diff check와 필수 runtime QA가 통과한다.
